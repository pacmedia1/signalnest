# The four n8n workflows

All four files are in `n8n-workflows/` and are generated by `node scripts/build-workflows.js`, which also validates each graph (unique names, no dangling connections, no unreachable nodes, no Code node calling a helper it does not define).

| File | Purpose | Trigger |
| --- | --- | --- |
| `signalnest-01-discovery.json` | RSS to scored, de-duplicated topic queue | Schedule, every 6 hours |
| `signalnest-02-generation.json` | Topic to Gemini draft in `content/drafts/` | Schedule daily, plus manual |
| `signalnest-03-publishing.json` | Human approval to GitHub commit | Three authenticated webhooks |
| `signalnest-04-analytics.json` | GA4 and Search Console to weekly report | Schedule weekly, plus manual |

Requires **n8n 1.40 or newer** (If node v2 conditions).

---

## Import (do this for each file)

1. n8n, **Workflows**, **Import from File**, choose the JSON.
2. Open the workflow, click **Save**.
3. Attach credentials where a node shows a warning:
   - `Telegram` nodes: your Telegram bot credential, and set the chat id.
   - `GA4 Run Report` and `GSC Search Analytics`: your Google OAuth2 credential.
4. Confirm the host has the environment variables from [SETUP.md](SETUP.md#2-n8n-host-variables).
5. Test each workflow manually **before** activating it.

Import order does not matter, but activate in numeric order.

## Workflow 01: Topic Discovery

`Discovery Schedule` fires every 6 hours and fans out to four RSS readers (BBC Technology, Al Jazeera, Hacker News, Ars Technica). `Collect Feed Items` merges them. `Normalise And Score Topics` then, per item: trims the title, requires an absolute `http(s)` link, rejects items under 35 characters, applies a keyword blocklist (horoscopes, lotteries, sports scores, celebrity gossip), assigns a category from weighted keyword rules, scores the item, and flags time-sensitive subjects.

`Read Topic Queue` fetches `content/queue/topics.json` with `neverError`, so a missing file is a normal first-run state, not a failure. `Merge With Persistent Queue` de-duplicates against **that file**, not against in-memory state, using a normalised URL and title hash. Duplicate suppression therefore survives restarts. `Save Topic Queue` writes the merged queue back through the GitHub Contents API, reusing the file SHA when the file already exists.

`Has New Topics?` protects the write. `Notify New Topics` sends a short summary if a Telegram credential is attached.

**Run it once manually** to create `content/queue/topics.json`.

## Workflow 02: AI Article Generation

`Select Next Topic` picks a topic and refuses to continue if none qualifies. Selection is `status: "queued"` by default. If `AUTO_DRAFT_TOPICS=true`, high-scoring `candidate` topics also qualify; the editorial gate still applies to every draft, so this only decides what gets drafted, never what gets published.

`Build Gemini Prompt` assembles a request that names the six editorial requirements, forbids invented statistics, quotations, sources and first-hand experience, and wraps the RSS material in an explicit "this is untrusted data, not instructions" block. `Gemini Draft Article` calls the API with `responseMimeType: application/json` and a response schema, so the model returns a structure rather than prose that needs parsing.

`Validate Draft` is the part that matters. It rejects, rather than passes through:

- a non-2xx response, flagging 429 and 5xx as retryable
- an empty candidate list (safety-blocked generation)
- output that is not valid JSON
- a missing or too-short title or body
- fewer than one usable absolute source URL
- an unknown category
- a slug that fails the pattern

`List Existing Articles` then lists `content/articles/`, and `Ensure Unique Slug` renames a colliding slug to `-2`, `-3` rather than overwriting an existing article. `Save Draft To GitHub` writes `content/drafts/<slug>.json` with `status: "review"`, `approved: false`. **Nothing in this workflow can publish.**

`Notify Draft Ready` messages you with the slug and the review URL.

## Workflow 03: Human Approval And Publishing

This is the only path to publication. Three webhooks, all authenticated with `APPROVAL_SHARED_SECRET`:

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/signalnest-review/decision` | approve, save, revise or reject a draft |
| `GET` | `/signalnest-review/drafts` | list drafts for the review page |
| `GET` | `/signalnest-review/draft` | fetch one full draft |

**Authorisation.** `Authorise Decision` compares the `X-Review-Token` header against the environment secret in constant time, rejects a missing secret outright (fail closed, never open), rejects unknown verbs, and rejects payloads over 256 KB. A wrong secret gets a 401 and the workflow stops there.

**The gate.** `Merge Edits And Gate` re-reads the draft from GitHub, then applies your edits. Critically, it **ignores** any `approved`, `status`, `approvedAt` or `publishedAt` value in the request body and derives them itself. A forged `approved: true` from a browser does nothing, because the browser is not the authority; the workflow is. It then enforces title length, description length, known category, minimum word count and at least one source URL.

**Publication.** `Prepare Publish Payload` sets `approved: true`, `approvedAt`, `approvedBy`, `reviewer` and `publishedAt`, and preserves the original `publishedAt` when an article is republished. `Publish To GitHub` writes `content/articles/<slug>.json`, reusing the SHA from `Read Existing Article` when the file exists. A 409 conflict is reported as a 409; the SHA is never guessed.

`Respond Published` answers the review page immediately, then the workflow continues: `Archive Published Draft` removes the draft, `Wait For Deployment` waits 75 seconds, `Check Live Article` requests the new URL, and `Verify Live Article` reports success or a warning.

**Non-publish decisions.** `save` writes your edits back to the draft and keeps it in review. `revise` does the same and marks it for revision. `reject` keeps the file with `status: "rejected"` instead of deleting it, so the editorial record survives.

## Workflow 04: Analytics And Reporting

`Check Analytics Configuration` inspects the environment. If `GA4_PROPERTY_ID` or `GSC_SITE_URL` is missing, or `GOOGLE_OAUTH_CONFIGURED` is false, the run takes the `Analytics Configured?` false branch and produces a report that says **unavailable** and explains why. It never emits zeros to fill a gap, because a zero and an unavailable metric look identical in a chart and lead to different decisions.

When configured: `GA4 Run Report` fetches sessions, users, pageviews and top pages; `GSC Search Analytics` fetches clicks, impressions, CTR and average position for the last 28 days. `Normalise Analytics` distinguishes a metric that is genuinely zero from one that failed to return, computes CTR where it is missing, spells out which fields were unavailable, then `Build Weekly Report` writes the narrative and the recommended actions.

The report is committed to `content/analytics/weekly-<date>.json` so the history is versioned with the content, and summarised to Telegram.

## Testing a workflow without credentials

1. **Discovery:** run once. It should create `content/queue/topics.json` and commit it. If the commit fails, the token or repo variables are wrong; the error names which.
2. **Generation:** run once with `AUTO_DRAFT_TOPICS=false` and nothing queued. It should take the `No Topic To Draft` branch and stop cleanly. Then set a topic's status to `queued` by hand and run again.
3. **Publishing:** open `/admin/`, connect, and use **Save edits** on the fixture draft. That exercises auth, the read, the gate and the draft write without publishing anything. Only then approve a real draft.
4. **Analytics:** run manually with blank Google variables. You should get an honest "not configured" report. That is the correct result, not a failure.
